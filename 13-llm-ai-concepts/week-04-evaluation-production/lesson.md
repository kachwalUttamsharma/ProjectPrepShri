## 1. Evaluation: the foundation

"Vibes" do not scale. An eval is a repeatable, versioned measurement of whether the system does what the customer needs. Without it you cannot change prompts, models or retrieval safely, and you cannot answer "is v2 better?".

### 1.1 Designing an eval set
- Source: real production queries/tickets (best), domain-expert-written cases, synthetic cases generated by an LLM then human-reviewed, red-team cases.
- Size: start with 50 to 100 well-chosen cases; grow to a few hundred; stratify by category, difficulty, language, length, customer segment. Enough that differences are not noise (a 2-point change on 50 cases is meaningless; compute confidence intervals or bootstrap).
- Include: typical cases, edge cases, adversarial/injection cases, unanswerable questions (expected: abstain), known past failures (every production bug becomes a test), and a held-out set you do not tune on.
- Labels: expected answer, rubric, or acceptance criteria; for generation, rubric items (must mention X, must not mention Y, must cite).
- Version the dataset, record how labelled, measure inter-annotator agreement on a sample.
- Avoid leakage: do not put eval examples into few-shot prompts or fine-tuning data; beware public benchmark contamination.

### 1.2 Metrics by task
| Task | Metrics |
|---|---|
| Classification/extraction | accuracy, per-class precision/recall/F1, exact match on fields, schema-valid rate |
| RAG retrieval | recall@k, MRR, nDCG |
| RAG generation | faithfulness (grounded in context), answer correctness, citation accuracy, abstention correctness |
| Summarization/free text | rubric scoring, pairwise preference, factual consistency checks |
| Agents | task success rate, steps, tool-call correctness, cost per success, forbidden-action rate |
| Safety | injection success rate, PII leakage rate, refusal correctness |
| Ops | latency p50/p95/p99, cost per request, error/timeout rate |

Prefer simple deterministic checks first (exact match, regex, schema, code execution, SQL result equality), then LLM judges for what cannot be checked mechanically, then humans for calibration.

### 1.3 LLM-as-judge and its pitfalls
Use a model to grade outputs against a rubric or compare two outputs. Scales cheaply, but:
- Position bias (prefers first/second answer): randomize order, run both orders.
- Verbosity bias (prefers longer): control for length, instruct to ignore it.
- Self-preference (a model favors its own family's style): use a different judge family, or multiple judges.
- Vague rubrics give noisy scores: use specific, binary or small-scale criteria, ask for reasoning then a score, include examples.
- Judge can be wrong on facts it does not know: supply reference answers or source context.
- Nondeterminism: low temperature, repeat and aggregate.
- Drift when the judge model changes: pin judge version.
- Always calibrate: have humans label 50 to 100 examples, compute judge-human agreement (e.g. Cohen's kappa or simple agreement); report it. Re-calibrate when rubric or judge changes.
- Do not judge with the same prompt you optimized against (overfitting to the judge).

### 1.4 Offline vs online
- Offline: fixed dataset, run before release; fast, repeatable, safe; limited by dataset representativeness.
- Online: real traffic. Shadow mode (run new version silently, compare), canary (small percent), A/B test with business metrics (resolution rate, handle time, CSAT, escalation rate, edit distance of user corrections), implicit feedback (thumbs, retries, copy/paste, abandonment), sampled human review of production logs.
- Loop: production failures become offline cases; offline gates deploys; online confirms value.

### 1.5 Regression testing prompts
Treat prompts like code: stored in version control, with an eval suite in CI. On every change (prompt, model version, retrieval config, tool schema), run the suite; fail the build on a drop beyond a tolerance on key metrics or any "must never fail" case. Compare per-category, inspect diffs of individual outputs, not just the mean. Pin model versions; run the suite when a provider announces deprecation.

Runnable mini eval harness (no API key; the "model" is a stub):

```python
import json, statistics

def fake_classifier(text: str) -> str:
    t = text.lower()
    if "invoice" in t or "charge" in t:
        return "billing"
    if "error" in t or "crash" in t:
        return "bug"
    return "other"

DATASET = [
    {"text": "I was charged twice", "label": "billing"},
    {"text": "App crash on login", "label": "bug"},
    {"text": "How do I export data?", "label": "how_to"},
    {"text": "Invoice 123 is wrong", "label": "billing"},
]

def evaluate(predict, data):
    rows = [(d["label"], predict(d["text"])) for d in data]
    acc = sum(1 for y, p in rows if y == p) / len(rows)
    labels = sorted({y for y, _ in rows})
    per_class = {}
    for c in labels:
        tp = sum(1 for y, p in rows if y == c and p == c)
        fp = sum(1 for y, p in rows if y != c and p == c)
        fn = sum(1 for y, p in rows if y == c and p != c)
        prec = tp / (tp + fp) if tp + fp else 0.0
        rec = tp / (tp + fn) if tp + fn else 0.0
        per_class[c] = {"precision": round(prec, 2), "recall": round(rec, 2)}
    return acc, per_class

acc, per_class = evaluate(fake_classifier, DATASET)
print("accuracy", acc)
print(json.dumps(per_class, indent=2))
assert acc >= 0.7, "regression gate failed"
```

## 2. Observability and tracing

Log and trace every request so you can answer "what happened and why?".
- Trace = tree of spans: request, retrieval (query, ids, scores), rerank, each LLM call (prompt version, model id, params, input/output tokens, latency, finish reason), each tool call (args, result, latency, errors), validation results.
- Metrics: latency percentiles (time to first token and total), tokens in/out, cost, error and timeout rates by cause (429, 5xx, validation), cache hit rate, tool failure rate, refusal rate, guardrail triggers, thumbs-down rate, empty-retrieval rate.
- Quality in production: sampled LLM-judge or human scoring of live traffic, drift detection on input distribution (new topics/languages), alerts on spikes.
- Correlation ID through all components; link feedback to trace ID.
- Privacy: redact PII/secrets before logging; retention limits; access control to logs; decide whether to log raw prompts at all for regulated customers.
- Tools: OpenTelemetry-style tracing plus LLM-specific observability products; pick by customer constraints (self-hosted vs SaaS). Do not name a winner.

## 3. Latency

Components: network, queueing, prefill (grows with prompt), decode (tokens times per-token time), tool calls, retrieval, rerank, post-processing.

Levers:
- Stream tokens (perceived latency; time to first token matters most for chat). Handle streaming with partial JSON carefully; validate at end.
- Shorter prompts, fewer retrieved chunks, smaller output (max_tokens, concise instructions).
- Smaller/faster model for easy steps; speculative or distilled options on self-hosted.
- Parallelize independent calls (retrieval + classification; multiple tool calls).
- Prompt caching for stable prefixes.
- Precompute: embeddings, summaries, popular answers.
- Regional endpoints, connection reuse, timeouts and hedged requests for tails.
- Set an SLO (e.g. p95 time to first token under N seconds, p95 total under M) and measure by percentile, not average.

## 4. Caching

- Prompt (prefix) caching: provider reuses computed prefix state for identical leading tokens; cached input tokens are billed lower and processed faster (check current docs for TTL, minimum size, pricing). Design prompts with static content first (system, tools, documents), dynamic content last; avoid inserting timestamps/user IDs early in the prompt.
- Response cache (exact): key = hash(model, prompt version, params, normalized input). Safe for deterministic, non-personalized requests. Respect TTL and invalidation when source data changes.
- Semantic cache: embed the query, return a stored answer if similarity above a threshold. Saves cost on repeated FAQs. Risks: false hits (similar but different question, e.g. "cancel order 12" vs "cancel order 21"), stale answers, cross-user leakage (scope the cache by tenant/permissions), threshold tuning needs an eval. Do not semantically cache anything personalized or high-stakes without strong keys.
- Tool-result caching for deterministic reads.
- Embedding cache keyed by content hash to avoid re-embedding.

## 5. Rate limits, batching, streaming

- Providers limit requests per minute and tokens per minute (and sometimes concurrency); limits differ by tier and model: check current docs. Expect HTTP 429 (and 5xx/overloaded).
- Client handling: exponential backoff with jitter, respect Retry-After headers, a token bucket or concurrency limiter in your own service, queue with priorities (interactive before batch), per-tenant fairness so one customer cannot starve others, circuit breaker and fallback model/provider, request timeouts.
- Capacity planning: peak requests per second times average tokens per request versus tokens-per-minute limit; request limit increases or provisioned throughput well ahead of launch.
- Batching: batch APIs (asynchronous, often discounted, hours to complete; check current docs) for offline work such as evals, backfills, embeddings, classification of archives. Not for interactive use. Also batch embedding inputs per request.
- Streaming: server-sent events/websockets; show tokens as they arrive; cancel generation when the client disconnects (saves cost); handle mid-stream errors; apply output guardrails on the stream with care (buffer when you must filter).

## 6. Cost estimation: worked examples

Formula: cost = (input_tokens * P_in + output_tokens * P_out) / 1e6, with possible cached-input discount. Use HYPOTHETICAL prices here: P_in = $1 per 1M, P_out = $4 per 1M (cheap tier); P_in = $5, P_out = $20 (large tier). Replace with current numbers.

Example A: support-ticket classifier. 300 input tokens, 20 output tokens, 100,000 tickets per day, cheap tier.
- Per call: 300*1/1e6 + 20*4/1e6 = 0.0003 + 0.00008 = $0.00038.
- Per day: 100,000 * 0.00038 = $38. Per month (30 d): about $1,140.
- With the large tier: 300*5/1e6 + 20*20/1e6 = 0.0015 + 0.0004 = $0.0019; per day $190; per month $5,700. Router sending 80 percent to cheap: 0.8*38 + 0.2*190 = $68.4 per day.

Example B: RAG answers. 6 chunks of 400 tokens + 300 prompt tokens = 2,700 input; 250 output; 20,000 queries per day; mid tier hypothetical $3/$12.
- Per call: 2,700*3/1e6 + 250*12/1e6 = 0.0081 + 0.003 = $0.0111.
- Per day: $222. If a 2,000-token static prefix is cached at a hypothetical 90 percent discount: input becomes 2,000*0.3/1e6 + 700*3/1e6 = 0.0006 + 0.0021 = 0.0027; total per call 0.0057; per day $114. Plus embedding, rerank, vector DB and infra: do not forget those lines.

Example C: agent. 8 steps, input grows (computed in Week 3: about 46,400 input tokens per task), output 1,500 tokens; mid tier $3/$12: 46,400*3/1e6 + 1,500*12/1e6 = 0.139 + 0.018 = $0.157 per task. If 40 percent of tasks fail and are retried by users, the cost per successful task is higher: 0.157 / 0.6 = about $0.26.

```python
def cost(in_tok, out_tok, p_in, p_out, cached_in=0, cache_discount=0.9):
    fresh = in_tok - cached_in
    return (fresh * p_in + cached_in * p_in * (1 - cache_discount) + out_tok * p_out) / 1e6

print(round(cost(2700, 250, 3, 12), 5))
print(round(cost(2700, 250, 3, 12, cached_in=2000), 5))
daily = 20_000 * cost(2700, 250, 3, 12, cached_in=2000)
print("per day", round(daily, 2), "per month", round(daily * 30, 2))
```

Levers: smaller model, routing, shorter prompts, fewer chunks, prompt caching, response caching, batch discounts for offline, output limits, stop sequences, fine-tuned small model, and rejecting bad requests early. Always present cost per business outcome (per resolved ticket) and compare with the human baseline.

## 7. Versioning

Version everything that affects behavior and log it with each request: prompt template (semantic version or git hash), model id (pin exact version, avoid floating aliases in prod), sampling params, tool schemas, retrieval config (embedding model, chunking, index version), guardrail rules, eval dataset version. Rollout: feature flag, canary, rollback plan, deprecation calendar for provider models (set reminders; run evals against successors early). Keep prompts in files/config under review, not scattered strings; changes require eval results in the PR.

## 8. Safety, PII and compliance

- Threats: prompt injection, data leakage (cross-tenant, training data, logs), PII in prompts, harmful or off-brand content, overreliance, excessive agency.
- Controls: input/output filters, PII detection and redaction/tokenization before sending to a third-party model, content moderation endpoints or classifiers, allowlisted tools, rate limits and abuse monitoring, red-teaming, human escalation, disclaimers for AI-generated content where required.
- Compliance topics: GDPR/CCPA (lawful basis, minimization, deletion, data subject requests, cross-border transfer), HIPAA (BAA with provider, PHI handling), SOC 2/ISO controls, industry rules (finance, health), audit logging, data residency, retention. Say "involve the customer's security/legal team; check provider terms for data use, retention and regional processing" rather than giving legal advice.
- Fairness and bias: evaluate across segments; document limits.

## 9. Fine-tuning basics

Fine-tuning updates model weights on your examples. Use for behavior (format, tone, domain style, classification boundaries), distilling a large model into a small cheap one, or cutting prompt length. Not for adding fast-changing facts (use RAG).

- Full fine-tune: update all weights; expensive, needs lots of GPU memory.
- LoRA (low-rank adaptation): freeze the base weights, train small low-rank matrices added to some layers (W + A*B, rank r small). Typically trains well under 1 percent of parameters, uses far less memory, and adapters are small files that can be swapped per task or customer. QLoRA: same with a quantized base model for even less memory.
- Managed fine-tuning APIs exist for some hosted models (check current docs); open-weights models can be tuned and self-hosted.

When it is worth it: prompting and few-shot plateau below target; high volume makes a smaller tuned model cheaper; strict format or style needs; latency requirements; you have hundreds to thousands of high-quality labeled examples; task is stable; you have an eval set to prove gains. Costs: data curation (the real cost), training runs, hosting, re-tuning when the base model changes, risk of overfitting or forgetting, loss of provider upgrades.

Order of operations: better prompt, then few-shot, then RAG/tools, then fine-tune. Always compare against the strong-prompt baseline.

## 10. Data privacy in customer deployments (FDE angle)

- Ask first: what data classes (PII, PHI, financial, trade secrets), where may data go (region, third-party processors), retention and training-use terms, who has access, audit needs.
- Deployment options, by control: provider API with zero-retention/no-training terms; cloud-hosted model within the customer's cloud account/VPC (private networking, customer-managed keys); self-hosted open-weights on customer infrastructure or air-gapped. More control means more ops burden and often lower capability.
- Minimize: send only the fields needed; redact or pseudonymize before the model, re-hydrate after; avoid logging raw content; encrypt at rest and in transit; per-tenant isolation in vector stores and caches.
- Access control: user identity flows to retrieval and tools; no shared super-user keys.
- Secrets management; least privilege IAM; audit trails; DPA/BAA paperwork; deletion workflow that covers vector store, caches, logs, backups.
- Be honest about tradeoffs and document the data-flow diagram; customers' security reviewers love a clear one.

## 11. How interviewers probe
- "How do you know it works?" (Eval set design, metrics, calibration, CIs.)
- "LLM judge: trust it?" (Biases, calibration with humans.)
- "Design the monitoring for this feature." (Traces, metrics, quality sampling, alerts, privacy.)
- "Estimate the monthly cost." (Token math, caching, routing, per-outcome.)
- "p95 latency is 12 seconds, fix it." (Decompose by span, then levers.)
- "We hit 429s at launch." (Backoff, limits, queueing, quota increase, fallback, batching.)
- "Should we fine-tune?" (Decision ladder, prerequisites.)
- "Customer's data cannot leave the EU/their VPC." (Deployment options, residency, redaction.)
