Week 2 - Interview Q&A: Data and Storage

How to use: cover the answer, say it out loud in 30-60 seconds, then compare. Numbers marked "check current docs" change. Related: lesson.md, ../../07-aws/week-03-storage-databases.

Q1. Why replicate data, and what does replication NOT give you? Availability (survive node/AZ loss), read scaling, and lower latency by locating copies near users. In single-leader systems it does not scale writes: every replica must apply every write. Write scaling needs partitioning.

Q2. Compare synchronous, asynchronous, and semi-synchronous replication. Sync: leader waits for follower ack; no loss on leader failure but a slow follower stalls writes. Async: ack immediately; fast but acknowledged writes can be lost on failover and followers lag. Semi-sync: one sync follower plus async rest so at least two copies exist; the usual compromise.

Q3. The leader crashes and the promoted follower was 2 seconds behind. What happens? With async replication the last ~2 s of acknowledged writes are missing on the new leader (RPO > 0). When the old leader returns, its extra writes are discarded or must be reconciled, which is dangerous if other systems already saw them (e.g., reused auto-increment IDs). Mitigate with semi-sync/sync replication, consensus-based election, fencing, and accepting a defined RPO.

Q4. What is split brain and how do you prevent it? Two nodes both believe they are leader and accept writes, diverging data. Prevent with majority-quorum election (Raft/Paxos/ZooKeeper/etcd), leases that expire, and fencing tokens or STONITH so a deposed leader cannot write.

Q5. A user posts a comment and refreshes; it is gone. Why and how do you fix it? Write went to the leader, the read hit a lagging follower: a read-your-writes violation. Fixes: read the user's own recent data from the leader for a short window, track last-write LSN/timestamp and only use caught-up replicas, or use sticky routing/session consistency. Related: monotonic reads fixed by pinning a user to one replica.

Q6. When would you choose multi-leader replication and what is the main cost? Multi-region active-active writes (local latency, tolerate inter-region link loss), offline-capable clients, collaborative editing. The cost is write conflicts. Strategies: avoid by home-region routing per entity, last-write-wins (lossy, clock-dependent), merge with CRDTs/OT or app-level resolution.

Q7. Explain quorum reads and writes. Does W+R>N give linearizability? With N replicas, a write needs W acks and a read queries R; if W+R>N the sets overlap so a read sees at least one replica with the latest write. Common: N=3, W=2, R=2. It is not linearizable in general: sloppy quorums and hinted handoff, LWW with clock skew, partially failed writes that are not rolled back, and in-flight concurrent writes can all produce stale or flipping reads. For true linearizability use consensus or compare-and-set (Cassandra LWT is Paxos-based).

Q8. What are read repair, hinted handoff, and anti-entropy? Read repair: during a read, stale replicas detected are updated. Hinted handoff: when a target replica is down, another node stores the write as a hint and delivers it on recovery. Anti-entropy: background comparison (Merkle trees) to sync replicas that missed writes. All are ways leaderless stores converge.

Q9. Range vs hash partitioning: trade-offs? Range keeps keys ordered so range scans are efficient and splitting is easy, but sequential keys (timestamps) cause hot spots. Hash spreads load evenly but kills range queries (scatter-gather). Hybrid: compound keys (hash partition key, sorted clustering/sort key) as in Cassandra and DynamoDB.

Q10. Why is hash(key) mod N a bad sharding scheme and what do you use instead? Changing N remaps nearly all keys, forcing a massive data migration. Use consistent hashing (only about K/N keys move when a node is added or removed), ideally with virtual nodes for even load and shared failure impact, or a fixed large number of partitions (Kafka partitions, Redis Cluster 16384 slots) that are reassigned whole.

Q11. What are virtual nodes and why do they matter? Each physical node owns many small token ranges on the ring. They even out data/load distribution, spread a failed node's load across many peers (avoiding one neighbor overload cascade), allow weighting by machine capacity, and make bootstrapping stream from many nodes in parallel.

Q12. How do you handle a hot key (celebrity user, viral item)? Detect it, then: cache in front (CDN/Redis/local cache), split the key with a random suffix and merge on read (or aggregate writes in memory before flush for counters), replicate hot data to more nodes, isolate big tenants on dedicated shards. Note hashing balances keys, not load. Managed stores (DynamoDB adaptive capacity) help but have per-partition limits (check current docs).

Q13. Local vs global secondary indexes on a sharded store? Local: index stored with each partition; writes are cheap and single-partition, but queries by the secondary attribute must scatter-gather to every shard (tail latency). Global: index partitioned by the indexed term; reads hit one shard but writes touch multiple shards and are usually async/eventually consistent (DynamoDB GSI). Pick based on read vs write ratio.

Q14. How do you choose the shard key? Look at dominant access patterns so common queries hit one shard; ensure high cardinality, even distribution, and no skewed write/read hot spot; avoid monotonically increasing keys on range partitioning; consider future growth and the cost of resharding. Examples: chat by conversation_id, orders by user_id, SaaS by tenant_id (watch for giant tenants), metrics by (series_id, time bucket).

Q15. SQL vs NoSQL: how do you decide? Decide from access patterns, consistency, and scale rather than ideology. Relational: ad hoc queries, joins, multi-row ACID transactions, moderate scale (a primary with replicas goes far). Wide-column/KV: massive write throughput, key-based access, predictable latency, known queries, denormalized per-query tables. Document: aggregate-shaped data and flexible schema. Distributed SQL (Spanner, CockroachDB): need SQL, transactions, and horizontal/geo scale at some latency cost. Often polyglot: RDBMS as source of truth plus search/cache/analytics derived via CDC.

Q16. B-tree vs LSM-tree? B-tree updates pages in place: strong read performance and range scans, write amplification and random IO. LSM buffers writes in memory plus WAL, flushes immutable sorted SSTables, and compacts in the background: very high write throughput, but reads may touch multiple files (Bloom filters help) and compaction causes IO spikes and space amplification. B-tree for read-heavy OLTP; LSM for write-heavy ingest (Cassandra, RocksDB).

Q17. A query on a 500M-row table is slow. What do you do? EXPLAIN ANALYZE; verify an index is used and the column order matches (leftmost prefix); add a covering or partial index; fix stale stats; replace OFFSET with keyset pagination; partition by time and archive; offload analytics to a replica/warehouse; add caching; denormalize/precompute; shard last. Also weigh write cost of extra indexes.

Q18. State CAP correctly. During a network partition a system must choose between consistency (linearizability) and availability (every non-failed node responds). Partition tolerance is not optional in a distributed system, so it is a C vs A choice during failure, and it is per operation/configuration rather than a fixed label. CAP's C is not ACID's C. Without a partition you can have both.

Q19. What does PACELC add? Else clause: when there is no partition, you still trade latency against consistency, because synchronous replication costs round trips. Cassandra/Dynamo are PA/EL, Spanner is PC/EC. It explains why we read feeds from a local replica but balances from the leader.

Q20. Explain strong, causal, read-your-writes, and eventual consistency, with a use case each. Strong (linearizable): single-copy illusion, real-time order; payments, locks, unique usernames. Causal: causally related ops are seen in order; chat replies after the message. Read-your-writes: you see your own updates; profile edits. Eventual: replicas converge if writes stop; like counts, feeds. Choose the weakest model that preserves the product's invariants, since stronger costs latency and availability.

Q21. How does Spanner provide strong consistency globally, and what is the cost? Data is range-split; each split is a Paxos group across zones/regions. TrueTime exposes bounded clock uncertainty, and a transaction waits out the uncertainty (commit-wait) before making a commit timestamp visible, giving external consistency (strict serializability). Cross-split transactions use two-phase commit among Paxos leaders. Cost: higher write latency and money, rising with replica distance.

Q22. What are isolation levels, and how do they differ from distributed consistency? Isolation (read committed, snapshot/repeatable read, serializable) governs how concurrent transactions on a database see each other and which anomalies (dirty read, lost update, write skew, phantom) occur. Distributed consistency is about whether replicas of the same data agree and in what order. They are separate axes; Spanner's strict serializability combines both.

Q23. Why do scatter-gather queries have bad tail latency? The request waits for the slowest shard. If each shard is slow 1% of the time and you query 100 shards, about 63% of requests hit at least one slow shard. Mitigate by avoiding scatter-gather (better keys, global index), hedged/backup requests, timeouts with partial results.

Q24. Resharding a live system: how do you do it safely? Prefer designs that avoid it (many fixed partitions, consistent hashing with vnodes, pre-splitting). When needed: add the new topology, copy data in the background, dual-write or use CDC to catch up, verify (checksums/shadow reads), switch routing atomically via the metadata store, keep the old copy for rollback, throttle to protect production, and avoid automatic triggers that could cascade under load.
