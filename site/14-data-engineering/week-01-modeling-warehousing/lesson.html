Week 1: Data Modeling and Warehousing

Goal: be able to take a vague business ("model a ride-sharing company") and, in 10 minutes at a whiteboard, declare the grain, name the facts and dimensions, pick SCD behavior, and explain how it lands in a columnar warehouse. Vendor details (Snowflake, BigQuery, Redshift) change often: items marked "(check current docs)" need verification before you quote them.

Run the demo: sqlite3 :memory: < scd2_demo.sql (file in this folder, verified on SQLite 3.54).

1. OLTP vs OLAP

OLTP OLAP
Purpose Run the business (orders, payments) Analyze the business
Access pattern Many small point reads/writes by key Few huge scans and aggregations
Schema Normalized (3NF), many tables Denormalized (star), few wide tables
Storage Row-oriented (B-tree indexes) Columnar, compressed, partitioned
Concurrency Thousands of short txns Tens of heavy queries
History Current state (updates in place) Historical, append-heavy
Examples Postgres, MySQL, DynamoDB Snowflake, BigQuery, Redshift, ClickHouse

HTAP and "zero-ETL" blur the line, but the access-pattern difference still drives design. Never run heavy analytics on the OLTP primary: use a replica, CDC to a warehouse, or both.

2. Normalization in one page

  • 1NF: atomic values, no repeating groups.
  • 2NF: no partial dependency on part of a composite key.
  • 3NF: no transitive dependency (non-key attribute depends only on the key). Mnemonic: "the key, the whole key, nothing but the key."
  • Why OLTP normalizes: single place to update, no update anomalies, small rows.
  • Why OLAP denormalizes: joins on billions of rows are expensive; analysts need few, understandable tables; storage is cheap and columnar compression eats the repetition (a repeated country string compresses to almost nothing with dictionary/RLE encoding).

3. Dimensional modeling (Kimball)

Four-step design process (memorize):

  1. Pick the business process (orders, rides, subscriptions billing).
  2. Declare the grain (what exactly is one row in the fact table).
  3. Identify the dimensions (who, what, where, when, how, why).
  4. Identify the facts (numeric measurements at that grain).

Declaring the grain first is the single most important habit. Every column must be true at that grain; mixing grains (order-level shipping fee on an order-line row) causes double counting when summed.

Star vs snowflake

  • Star: fact table surrounded by denormalized dimensions (one join hop). Fast, simple, BI-friendly. Default choice.
  • Snowflake: dimensions normalized into sub-dimensions (product -> category -> department). Saves little space, adds joins and confusion. Use sparingly: when a sub-dimension is shared and changes independently, or the hierarchy is huge.
  • Galaxy / constellation: several facts sharing conformed dimensions.

Fact table types

Type One row per Example Notes
Transaction Event at a point in time Order line, payment, ride Most common, sparse, additive measures
Periodic snapshot Entity per period (day/month) Daily account balance, daily inventory Dense; includes rows even with no activity; semi-additive measures (balance)
Accumulating snapshot Process instance through a pipeline Order: placed, paid, shipped, delivered Row is UPDATED as milestones hit; multiple date keys; lag measures
Factless Event with no numeric measure Student attended class, promo eligibility Count rows; also "coverage" tables to find what did NOT happen

Additivity: additive (sum across all dims: revenue), semi-additive (sum across some dims, not time: balance, inventory on hand), non-additive (ratios, unit price: store numerator and denominator instead and divide at query time).

Dimensions

  • Surrogate key: meaningless integer (or hash) generated by the warehouse. Why: insulates from source key changes and reuse, enables SCD2 (several rows per natural key), smaller joins, handles "unknown" members (key -1 / 0). Hash-based surrogates (md5 of natural key plus version) are common in dbt and parallel loads; trade-off is wider keys and collision theory (negligible with 128+ bits).
  • Natural / business key: the source ID. Keep it as an attribute.
  • Degenerate dimension: a dimension attribute stored in the fact with no dimension table (order number, invoice number, ticket id). Useful for grouping lines into the parent document.
  • Role-playing dimension: same dimension used several times (order_date, ship_date, delivery_date all point to dim_date). Create views or aliases.
  • Junk dimension: combine low-cardinality flags/indicators (is_gift, payment_method, channel) into one small dimension instead of many flag columns on the fact.
  • Conformed dimension: shared, identically defined dimension across facts/marts (dim_customer, dim_date). It is what makes "drill across" possible and is the core of the Kimball bus architecture (enterprise bus matrix: processes as rows, conformed dims as columns).
  • Mini-dimension: split rapidly changing attributes (income band, credit score band) out of a big SCD2 dimension to prevent row explosion.
  • Outrigger: dimension referencing another dimension (snowflaking light).
  • Bridge table: resolves many-to-many between fact and dimension (a patient with multiple diagnoses, an account with multiple owners) or ragged hierarchies. Often carries a weighting factor so measures are allocated and do not double count.
  • Multi-valued dimension without bridge: pitfall is fan-out.
  • Date dimension: pre-built, one row per day, with fiscal periods, holidays, week numbers. Do not compute these in queries. Time of day is a separate dimension.
  • Unknown / not applicable members: seeded rows so fact FKs are never NULL (inner joins then never drop facts).

4. Slowly Changing Dimensions

Type Behavior History Use when
0 Never changes n/a Original signup date, birth date
1 Overwrite None Typo fixes, non-analytical attributes
2 New row per version (valid_from, valid_to, is_current) Full Default for attributes that matter historically (region, segment)
3 Extra column for previous value One step Rare: "previous region" analysis, planned re-orgs
4 Current table + history table (mini-dim / history) Full, separated Fast-changing attributes
6 1+2+3 hybrid: SCD2 rows plus a "current value" column overwritten on every version Full + as-is view Report both "as-was" and "as-is" without self-join
7 Dual keys in the fact (surrogate version key plus durable natural key) Full Similar goal to 6 via joins

Key mechanics of SCD2:

  • Fact rows reference the surrogate key of the version valid at event time. Facts never get re-pointed when the dimension changes.
  • Tracked attributes: decide which columns trigger a new version (city yes, phone no -> SCD1).
  • Close old row (valid_to = effective_date, is_current = 0), insert new row. Use half-open intervals valid_from <= t < valid_to so there are no gaps or overlaps. 9999-12-31 as open end is conventional.
  • Change detection: compare columns or a hash of tracked columns.
  • Effective date: use the business effective date when the source has it, otherwise load/ingestion time. Say which one you chose; interviewers probe this.
  • Idempotency: re-running the same batch must not create duplicate versions. Guard with the NOT EXISTS current row pattern (see demo) and a unique partial index on (natural_key) WHERE is_current.
  • Late-arriving data: see section 6.

Runnable demo: star schema + SCD2 (sqlite3)

Source of truth is scd2_demo.sql; here is the same file.

-- scd2_demo.sql : star schema + SCD Type 2 in sqlite3-compatible SQL
-- Run: sqlite3 :memory: < scd2_demo.sql
-- Needs SQLite >= 3.25 (window functions) and >= 3.35 not required.

PRAGMA foreign_keys = ON;

-- ---------- 1. Dimensions ----------
CREATE TABLE dim_date (
  date_key     INTEGER PRIMARY KEY,   -- smart key yyyymmdd (acceptable for date dim)
  full_date    TEXT NOT NULL,
  year         INTEGER, month INTEGER, day INTEGER
);

CREATE TABLE dim_product (
  product_key  INTEGER PRIMARY KEY,   -- surrogate
  product_id   TEXT NOT NULL,         -- natural / business key
  name         TEXT NOT NULL,
  category     TEXT NOT NULL
);

-- SCD2 customer dimension
CREATE TABLE dim_customer (
  customer_key   INTEGER PRIMARY KEY AUTOINCREMENT,  -- surrogate, one per version
  customer_id    TEXT NOT NULL,                      -- natural key
  name           TEXT NOT NULL,
  city           TEXT NOT NULL,                      -- tracked attribute
  segment        TEXT NOT NULL,                      -- tracked attribute
  valid_from     TEXT NOT NULL,
  valid_to       TEXT NOT NULL DEFAULT '9999-12-31',
  is_current     INTEGER NOT NULL DEFAULT 1
);
CREATE UNIQUE INDEX ux_customer_current ON dim_customer(customer_id) WHERE is_current = 1;

-- ---------- 2. Fact (grain: one row per order line) ----------
CREATE TABLE fact_sales (
  order_id      TEXT NOT NULL,            -- degenerate dimension
  line_no       INTEGER NOT NULL,
  date_key      INTEGER NOT NULL REFERENCES dim_date(date_key),
  customer_key  INTEGER NOT NULL REFERENCES dim_customer(customer_key),
  product_key   INTEGER NOT NULL REFERENCES dim_product(product_key),
  quantity      INTEGER NOT NULL,
  amount        REAL NOT NULL,
  PRIMARY KEY (order_id, line_no)
);

-- ---------- 3. Seed ----------
INSERT INTO dim_date VALUES
 (20240101,'2024-01-01',2024,1,1),
 (20240215,'2024-02-15',2024,2,15),
 (20240601,'2024-06-01',2024,6,1);
INSERT INTO dim_product VALUES (1,'P1','Widget','Hardware'),(2,'P2','Gadget','Hardware');

-- Initial load (day 1)
INSERT INTO dim_customer (customer_id,name,city,segment,valid_from)
VALUES ('C1','Asha','Pune','SMB','2024-01-01'),
       ('C2','Ben','Austin','Enterprise','2024-01-01');

-- Fact row before the change: points at the OLD version of C1
INSERT INTO fact_sales VALUES
 ('O1',1,20240101,(SELECT customer_key FROM dim_customer WHERE customer_id='C1' AND is_current=1),1,2,20.0);

-- ---------- 4. SCD2 change feed ----------
CREATE TABLE stg_customer (customer_id TEXT, name TEXT, city TEXT, segment TEXT, effective_date TEXT);
INSERT INTO stg_customer VALUES
 ('C1','Asha','Mumbai','SMB','2024-02-15'),        -- city changed
 ('C2','Ben','Austin','Enterprise','2024-02-15'),  -- unchanged
 ('C3','Chen','Berlin','SMB','2024-02-15');        -- brand new

-- Step A: close current rows whose tracked attributes differ
UPDATE dim_customer
SET valid_to = (SELECT s.effective_date FROM stg_customer s WHERE s.customer_id = dim_customer.customer_id),
    is_current = 0
WHERE is_current = 1
  AND EXISTS (SELECT 1 FROM stg_customer s
              WHERE s.customer_id = dim_customer.customer_id
                AND (s.city <> dim_customer.city OR s.segment <> dim_customer.segment));

-- Step B: insert new versions for changed + new customers (no current row exists now)
INSERT INTO dim_customer (customer_id,name,city,segment,valid_from)
SELECT s.customer_id, s.name, s.city, s.segment, s.effective_date
FROM stg_customer s
WHERE NOT EXISTS (SELECT 1 FROM dim_customer d WHERE d.customer_id = s.customer_id AND d.is_current = 1);

-- Fact load AFTER change: look up the version valid on the transaction date
INSERT INTO fact_sales
SELECT 'O2',1,20240215,
       (SELECT customer_key FROM dim_customer
         WHERE customer_id='C1' AND '2024-02-15' >= valid_from AND '2024-02-15' < valid_to),
       2,1,15.0;

-- ---------- 5. Checks / demo queries ----------
.headers on
.mode column
SELECT '--- dim_customer versions ---' AS info;
SELECT customer_key,customer_id,city,valid_from,valid_to,is_current FROM dim_customer ORDER BY customer_id,valid_from;

SELECT '--- sales by city AS-WAS (historical truth) ---' AS info;
SELECT c.city, SUM(f.amount) AS revenue
FROM fact_sales f JOIN dim_customer c USING (customer_key)
GROUP BY c.city ORDER BY c.city;

SELECT '--- sales by CURRENT city AS-IS (join on natural key to current row) ---' AS info;
SELECT cur.city, SUM(f.amount) AS revenue
FROM fact_sales f
JOIN dim_customer v   ON v.customer_key = f.customer_key
JOIN dim_customer cur ON cur.customer_id = v.customer_id AND cur.is_current = 1
GROUP BY cur.city ORDER BY cur.city;

SELECT '--- integrity: exactly one current row per customer (expect 0 rows) ---' AS info;
SELECT customer_id, COUNT(*) FROM dim_customer WHERE is_current=1 GROUP BY 1 HAVING COUNT(*)<>1;

SELECT '--- integrity: no overlapping validity ranges (expect 0 rows) ---' AS info;
SELECT a.customer_id FROM dim_customer a JOIN dim_customer b
  ON a.customer_id=b.customer_id AND a.customer_key<b.customer_key
 AND a.valid_from < b.valid_to AND b.valid_from < a.valid_to;

SELECT '--- idempotency: re-run steps A and B, row count must stay 4 ---' AS info;
UPDATE dim_customer
SET valid_to = (SELECT s.effective_date FROM stg_customer s WHERE s.customer_id = dim_customer.customer_id), is_current = 0
WHERE is_current = 1 AND EXISTS (SELECT 1 FROM stg_customer s WHERE s.customer_id = dim_customer.customer_id
      AND (s.city <> dim_customer.city OR s.segment <> dim_customer.segment));
INSERT INTO dim_customer (customer_id,name,city,segment,valid_from)
SELECT s.customer_id, s.name, s.city, s.segment, s.effective_date FROM stg_customer s
WHERE NOT EXISTS (SELECT 1 FROM dim_customer d WHERE d.customer_id = s.customer_id AND d.is_current = 1);
SELECT COUNT(*) AS rows_after_rerun FROM dim_customer;

Expected result: C1 has two versions; "as-was" report splits revenue Pune 20 / Mumbai 15; "as-is" report attributes all 35 to Mumbai; both integrity queries return no rows; re-running steps A/B leaves 4 rows.

Other SCD types in SQL (sqlite3 verified)

-- SCD1: overwrite
UPDATE dim_customer SET city = 'Mumbai' WHERE customer_id = 'C1';

-- SCD3: keep previous value in a column
ALTER TABLE dim_customer ADD COLUMN prev_city TEXT;
UPDATE dim_customer SET prev_city = city, city = 'Mumbai' WHERE customer_id = 'C1' AND city <> 'Mumbai';

-- SCD6: SCD2 rows + current_city column refreshed on ALL versions of that customer
ALTER TABLE dim_customer ADD COLUMN current_city TEXT;
UPDATE dim_customer SET current_city = (
  SELECT c2.city FROM dim_customer c2 WHERE c2.customer_id = dim_customer.customer_id AND c2.is_current = 1);

In a warehouse the SCD2 change is done with MERGE (Snowflake/BigQuery/Redshift/Delta all support it, syntax differs: check current docs) or, in dbt, with snapshots (week 3). Typical MERGE pattern: first statement closes changed rows, second inserts new versions; or a single MERGE using a UNION of "update the old row" and "insert the new row" source rows keyed with a NULL merge key trick.

5. Kimball vs Inmon vs Data Vault

Kimball Inmon Data Vault 2.0
Approach Bottom-up: business-process marts using conformed dimensions Top-down: normalized (3NF) enterprise warehouse first, marts derived Hub / Link / Satellite raw vault, then business vault and marts
Strength Fast delivery, user-friendly, great BI performance Single integrated truth, consistent Auditability, parallel loading, easy source onboarding, tolerant of schema change
Weakness Conformance discipline needed; reworking grain is painful Slow, upfront heavy More tables and joins; needs a presentation layer on top; heavier skill demand
Use when Most analytics teams Large enterprise with strong central governance Many sources, regulatory audit, frequent source change

Data Vault pieces: Hub = unique business keys; Link = relationships (many-to-many by default); Satellite = descriptive attributes with load date and hash diff (history). Everything insert-only and source-tracked. In practice: raw vault (as-is, auditable) feeds star-schema marts for consumption. A modern pragmatic pattern: raw -> staging -> intermediate -> marts (star), which is Kimball presentation with dbt.

"One Big Table" (wide denormalized table) is common in columnar warehouses for simple use cases: fewest joins, but duplicates dimension attributes, makes SCD handling and governance harder, and large rebuilds when a dimension changes. Often used as a derived layer on top of a star.

6. Late-arriving data

  • Late-arriving fact (event for a time already loaded): fine for facts; load it; look up the dimension version valid at event time (range join with valid_from <= event_ts < valid_to). Incremental pipelines need a lookback window or watermark that re-reads recent partitions; aggregates need rebuild of affected partitions.
  • Early-arriving fact / late-arriving dimension (fact references a customer not yet in the dimension): insert an "inferred member" row (natural key, attributes unknown, flagged is_inferred) so the fact has a valid surrogate key; when the real dimension row arrives, overwrite the inferred row (SCD1 style for first real load) rather than creating a version.
  • Late-arriving dimension change (a change effective in the past, e.g. customer moved last month, reported today): requires splitting the existing version: close the version at the effective date, insert the new row with valid_from = effective, valid_to = old valid_to, and re-point fact rows with event dates in the affected window. This is why many teams accept "effective as of load time" and document the limitation.
  • Event time vs processing time; use a watermark / allowed lateness (details in week 4). Keep both timestamps on the fact.
  • Idempotent, partition-overwrite loads (replace date partition) make reprocessing safe.

7. Columnar warehouses (concepts)

Why columnar: analytic queries touch few columns of many rows; columns stored contiguously compress well (dictionary, run-length, delta, bit-packing) and allow vectorized execution and skipping blocks via min/max metadata. Cost: slow single-row updates/inserts, so loads are bulk/batch and updates are expensive (rewrite or delta + merge).

Concepts shared by all:

  • Separation of storage and compute (Snowflake, BigQuery; Redshift RA3/Serverless) vs coupled (older Redshift node types, on-prem MPP). Lets you scale and pause compute independently; cost shifts to compute-time or bytes-scanned.
  • MPP: data distributed across nodes; joins require co-location or shuffling/broadcast. Data skew creates hot nodes.
  • Pruning: skip data that cannot match a filter, via partitions or per-block min/max metadata.
Concept Snowflake BigQuery Redshift
Billing model Compute credits per warehouse-second (min 60s on resume) plus storage On-demand: bytes scanned; or capacity (slots) editions (check current docs) Provisioned nodes or Serverless RPUs (check current docs)
Physical layout Automatic micro-partitions (small immutable files), metadata with min/max per column Capacitor columnar storage; you declare partitioning and clustering Slices; sort keys and distribution keys
Pruning control Clustering keys (automatic reclustering costs credits; only worth it for very large tables) Partition by date/integer/ingestion time; cluster by up to 4 columns (check current docs) Sort key (compound / interleaved), zone maps
Join co-location Not user-managed Not user-managed Distribution style: KEY, ALL (small dim), EVEN, AUTO

Partitioning vs clustering: partitioning splits a table into separate segments, best on a low-to-medium cardinality, commonly filtered column (event date); pruning is exact and cost estimates are predictable. Clustering/sort orders data within partitions to make min/max stats tight, helping range filters and joins on higher cardinality columns (customer_id). Over-partitioning (too many tiny partitions) hurts: metadata overhead and small files.

Cost control checklist (the answer interviewers want):

  • Select only needed columns; never SELECT * on columnar engines (billing/IO scales with columns read).
  • Filter on the partition column; require partition filter where supported.
  • Pre-aggregate/materialize repeated heavy queries (materialized views, incremental dbt models).
  • Right-size and auto-suspend compute; separate warehouses per workload (ELT, BI, ad hoc) with per-workload budgets/resource monitors and query timeouts.
  • Prefer incremental over full refresh.
  • Monitor top queries by cost via the query history views; tag queries by team.
  • Beware of cross joins, exploding joins, ORDER BY without LIMIT, repeated DISTINCT on huge sets, UDFs row-by-row.
  • Storage: expire/transient tables for staging, shorten time travel on high-churn tables, tiering of cold data.
  • Use result caching but do not depend on it.

Workload management pattern: isolate (ELT vs BI vs data science) into separate compute pools; set priorities; add queueing/concurrency limits; use autoscale for BI spikes; guard rails (statement timeouts, max bytes billed in BigQuery).

8. ETL vs ELT

  • ETL: transform before load, on a separate engine (Informatica, SSIS, Spark). Used when the target is expensive/limited, or sensitive data must be scrubbed before landing.
  • ELT: load raw first, transform inside the warehouse with SQL (dbt). Wins when warehouse compute is elastic, you want to keep raw data for replay, and analysts own transformations in SQL.
  • Real systems are mixed: EL (Fivetran/Airbyte/CDC/Kafka connect) into a raw layer, then T in SQL, with Spark for heavy or non-SQL work (ML features, unstructured parsing).
  • Layers: raw/bronze (immutable as-landed) -> staging/silver (typed, deduplicated, renamed) -> marts/gold (star schemas, metrics).
  • Always keep raw immutable: lets you fix logic bugs and backfill without re-extracting.

9. Modeling case prompts with answer sketches

Use this skeleton every time: business process -> grain -> facts -> dimensions -> SCD choices -> tricky parts -> queries it must answer.

  1. E-commerce orders. - Fact: fact_order_line grain = one product on one order. Measures: quantity, gross_amount, discount, tax, net_amount. Degenerate: order_id, line_no. - Dims: date (role-playing: order, ship), customer (SCD2 for segment/region), product (SCD2 price tier? usually SCD1 for name, SCD2 for category), geography, promotion, channel (junk dim), payment method. - Order-level fees (shipping): allocate to lines or place in a separate fact_order at header grain. Never mix grains. - Also: accumulating snapshot fact_order_fulfillment (placed, paid, packed, shipped, delivered dates; lag days). Returns: separate fact with negative or separate return rows.
  2. Ride-sharing (Uber-like). - Fact: fact_trip grain = one completed trip (cancelled trips in a separate fact or status dim). Measures: distance, duration, fare, surge_multiplier, driver_payout, tip. - Dims: rider, driver (SCD2: vehicle, rating tier, city), vehicle, pickup/dropoff location (role-playing; geohash/H3 cell dimension), date, time of day, product type (pool, black), payment. - Accumulating snapshot for trip lifecycle (requested, matched, pickup, dropoff). Periodic snapshot for driver daily online hours/utilization. Late events from mobile apps: event time vs server time.
  3. Subscription business (SaaS). - Facts: fact_invoice_line (transaction), fact_subscription_daily or fact_mrr_monthly (periodic snapshot: MRR by customer/plan/month), plus fact_subscription_event (start, upgrade, downgrade, cancel). - Dims: customer, plan (SCD2 price changes), date, promo, billing cycle. - MRR movements (new, expansion, contraction, churn, reactivation) are derived by comparing consecutive snapshots; churn definitions must be agreed and documented. Semi-additive MRR.
  4. Banking / accounts. - Periodic snapshot fact_account_balance_daily (balance semi-additive) plus transaction fact fact_transaction. Bridge table bridge_account_customer (joint accounts, weighting). SCD2 on customer risk tier. PII governance: tokenization, column masking.
  5. Ad impressions/clicks (adtech). - Very high volume fact at impression grain, partitioned by event date, clustered by campaign. Dims: campaign, creative, placement, device, geography. Click and conversion facts linked via impression_id (degenerate) with attribution window logic. Approximate distinct counts (HyperLogLog) for uniques. Often aggregated into hourly rollups for dashboards.
  6. Streaming/content platform (watch events). - Fact fact_playback_session grain = one viewing session; measures watch_seconds, buffer_events. Dims: user, title (hierarchy: show -> season -> episode, ragged: use bridge or flatten), device, date, time, geography. Daily snapshot for DAU/MAU precomputations. Sessionization of raw events is the hard part (gap-based windows).
  7. Healthcare encounters. - Fact fact_encounter. Patient can have many diagnoses: bridge table bridge_encounter_diagnosis with weighting factor, or a diagnosis-group dimension. Factless fact for appointment scheduling. HIPAA: de-identify, row/column level security, audit.
  8. Inventory and supply chain. - Periodic snapshot fact_inventory_daily (on-hand semi-additive), transaction fact for movements (receipt, sale, transfer, adjust), accumulating snapshot for purchase-order lifecycle. Dims: product, warehouse, supplier, date. Reorder analytics need snapshots with zero rows for no-movement days (dense).
  9. HR / org hierarchy (employees, managers). - SCD2 employee dimension (department, manager, level) so headcount at any date is correct. Hierarchy: self-referencing manager_id is hard in BI; materialize path/level columns or a bridge (ancestor, descendant, depth) for ragged hierarchies. Factless fact for position assignment.
  10. Marketplace (buyers, sellers, listings).
    • Two-sided; facts: fact_order_line, fact_listing_event, fact_payout. Conformed dims across them: seller, buyer, category, date. Seller and buyer might be the same person: make a conformed dim_party with role flags or two role dims referencing one underlying entity.
  11. IoT / sensor telemetry.
    • Huge append-only fact at reading grain, partitioned by day, aggregated to 1-min/1-hour rollups; dims: device (SCD2 firmware), location, sensor type. Late/out-of-order events, deduplication on (device_id, ts). Consider time-series DB for hot data, warehouse/lakehouse for history.
  12. Customer 360 / identity resolution.
    • Source customer IDs from CRM, web, billing. Build dim_customer with a durable surrogate "golden" key and a crosswalk table (source_system, source_id -> customer_key) with match confidence. Merges and unmerges: keep crosswalk history; never delete keys; fact rows may need re-pointing (SCD7 style durable key helps).
  13. Clickstream / web analytics.
    • Raw events at event grain; sessionize; fact_page_view, fact_session; dims: page, user (anonymous id to user id stitching), campaign (UTM), device, geography. Bot filtering, time zone handling.
  14. Ledger / finance (GL).
    • fact_gl_entry grain = one journal line, debit/credit signed measure. Dims: account (hierarchical chart of accounts with versioning), cost center, legal entity, date/fiscal period, currency. Multi-currency: store transaction currency amount, functional currency amount, and rate used; separate rate dimension/fact. Reconciliation: totals must tie to source.

Generic probes to be ready for: "what is the grain?", "how do you handle a product moving category?", "how do you backfill?", "how do you keep dimension and fact consistent?", "what is the PK of the fact?", "how would this change if volume grew 100x?", "how do you test it?" (uniqueness of grain, not-null FKs, referential integrity, row-count reconciliation, sum tie-out to source).

10. Pitfalls

  • Fan-out joins: joining a fact to a bridge/multi-valued dim without weights, or joining two facts of different grains directly. Aggregate each fact to a common grain first, then join (drill-across).
  • Summing non-additive or semi-additive measures.
  • Using the natural key in the fact for SCD2 dimensions (loses history, joins to multiple rows).
  • NULL foreign keys (use unknown member).
  • Time zones: store UTC timestamps; derive the local date key explicitly.
  • Overusing SCD2 on every attribute (row explosion, slow loads) or on high-churn columns.
  • Treating the star schema as a one-time design rather than evolving with conformed dimensions.
  • Not documenting grain and metric definitions (same word, two meanings).
